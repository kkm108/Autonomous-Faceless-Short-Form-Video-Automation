# Tasks.md — Remediation & Hardening Plan

**Repo reviewed:** `kkm108/Autonomous-Faceless-Short-Form-Video-Automation` (the `automato` CLI)
**Review basis:** every file in the repository was read in full — all 24 Python modules, both docs, `requirements.txt`, `config-snapshot.json`, and the workflow manifest — against the `main` branch as of 2026‑09‑02 (the repo's only commit at review time).
**How to use this file:** work each round to completion — including its "future-proof additions," which are prerequisites for the next round, not optional extras — before starting the next. The rounds aren't an arbitrary split: each one contains weaknesses that either exist right now, or only become visible/relevant once the previous round's fixes are actually in place (e.g. you can't usefully add CI until the crash bugs are fixed; cross-platform gaps only start blocking you once that CI exists and runs on Linux). Keep the IDs (`R1-W1`, `R1-F1`, ...) in commit messages so progress stays traceable.

## Round 1 — Fix what's actively broken, and stop new breakage from shipping

### Weaknesses (ordered by impact)

- [x] **R1-W1 — Critical: the self-healing "recovery" feature crashes every time it succeeds.**
  `automato/resilience/recovery.py`, function `_learn_if_stable()`. After its `try/except`, the function has three leftover lines (`if ok: log.info(...); return ok`) duplicating the true ending of `attempt_recover()` two functions above. `ok` and `choice` are never defined inside `_learn_if_stable` (its params are only `locs, group_name, cand, page`), so this raises `NameError` unconditionally, every time it's reached. Since `_learn_if_stable` is called right after a *successful* recovery click, **the one moment the LLM-recovery system works is the moment it throws an unrelated crash**, which the orchestrator wraps and lets kill the whole run — worse than not having recovery at all, since the logs show "Recovery succeeded..." right before the crash. It also means no selector is ever actually learned, so recovery re-pays its LLM round-trip every single time the same drift occurs. Fix: delete the stray duplicate lines; add a regression test that calls `_learn_if_stable` directly with a mocked `page`/`locs`.

- [x] **R1-W2 — Critical: the documented "guaranteed" TTS fallback chain is missing its dependencies.**
  `requirements.txt` lists only `playwright` and `pillow`. `automato/adapters/tts/kokoro_tts.py` imports `edge_tts` and `pyttsx3` for links 2 and 3 of the `auto` TTS chain, which the module's own docstring calls "guaranteed to produce audio." A clean install via the README's own `pip install -r requirements.txt` will `ModuleNotFoundError` the instant the primary browser path — explicitly documented in the same file as "flaky" — fails, which is exactly when the fallback is needed. Fix: add both packages to `requirements.txt` (with the Windows-conditional extra `pyttsx3` needs for its SAPI5 backend), and add a startup check that the packages needed for the *configured* `TTS_PROVIDER` are actually importable.

- [x] **R1-W3 — High: the retry contract for the riskiest stage is decorative, and its idempotency check has a gap.**
  `ExecutorError.retryable` (`automato/adapters/base.py`) is set in 5 places and read in exactly 0 (confirmed by search across the codebase). Most importantly, `automato/adapters/publish/youtube_studio.py` raises it with `retryable=True` specifically for "the upload may have succeeded but we couldn't confirm it," with a comment explaining why that distinction matters — but nothing consumes the flag, so the run just dies and a human must notice and type `--resume`. Worse: on that exact resume, `_load_previous()` only checks for a local `post_url.json`, which is precisely the file that failed to get written in this failure mode — so resuming after this specific error can **re-run the entire upload flow and publish the same video twice**. Fix: either implement real stage-level retry driven by `.retryable`, or — simpler and safer — have the publish adapter write a durable "upload attempted at T" marker *before* clicking Publish, and check YouTube Studio's own recent-uploads list on resume before ever re-submitting the file input.

- [x] **R1-W4 — High: no top-level error handling in the CLI.**
  `automato/__main__.py`: `main()` calls `args.func(args)` with no `try/except` (only `cmd_restore` handles its own errors). Any unhandled exception — including R1-W1's `NameError` — surfaces as a raw Python traceback with a non-obvious exit code, which is the wrong failure mode for a tool meant to run unattended via a scheduler. Fix: wrap `args.func(args)`, log the full traceback, print one clear summary line, and return a stable non-zero exit code.

- [x] **R1-W5 — High: rate-limit detection is prone to false positives in the one flow that matters most.**
  `automato/resilience/rate_limit.py`'s `looks_rate_limited()` treats generic substrings like `"a moment"`, `"quota"`, `"please wait"`, `"temporary"`, and `"cloudflare"` — found *anywhere* in the page's visible text — as a rate-limit signal, and this check runs before every single interaction. YouTube Studio's own normal, non-rate-limited "processing — please wait a moment" copy during an ordinary upload is a plausible false trigger, injecting a random 10–90s sleep (`config.RATE_LIMIT_MIN_WAIT_S`/`MAX_WAIT_S`) before each subsequent click for as long as that text is on screen. The same codebase already solves this correctly elsewhere: `automato/resilience/challenge.py` requires either a *strong*, unambiguous phrase or a *structural* DOM signal before weak/generic tokens count. Fix: port that strong/weak + structural-confirmation pattern into `rate_limit.py`.

- [x] **R1-W6 — High: no safe failure path when a challenge appears during a headless/unattended run.**
  `automato/resilience/challenge.py`'s `wait_for_human()` is built for an attended, headed session (prints to console, polls for a human-created flag file). In `--headless` mode — documented as "best for unattended scheduled runs" — there's no human to see the prompt. After `CHALLENGE_PAUSE_SECONDS` (180s default) it returns `False`, and its only caller, `ElementInteractor.goto()` in `interaction.py`, just logs a warning and keeps going against a page still behind the wall — risking confusing cascade failures, or a misfired click from the equally broad `ModalDismisser`. Fix: when running headless and a challenge is detected, fail the stage fast with a dedicated, clearly-named exception instead of degrading into an unpredictable continuation.

- [x] **R1-W7 — Medium-High: FFmpeg calls have no timeout and swallow their own error output.**
  `automato/adapters/assembly/ffmpeg.py`: both `subprocess.run(..., check=True, capture_output=True)` calls, plus `_probe_duration`'s `ffprobe` call, have no `timeout=` — a stuck encode hangs the whole pipeline forever with zero recovery, making the one dependency-free *local* stage the least resilient stage in the pipeline. `capture_output=True` also means a real ffmpeg failure (bad codec params, a corrupt frame, disk full) raises with a useless `"returned non-zero exit status 1"` and the actual stderr is never logged anywhere. Fix: add a sane `timeout=` to each call, and log `exc.stderr` on `CalledProcessError` before re-raising.

- [x] **R1-W8 — Medium: caption overflow silently deletes the beginning of the caption, not the end.**
  `automato/adapters/assembly/ffmpeg.py`, `_draw_text_wrapped()`: `while len(lines) > CAPTION_STYLE["lines"]: lines.pop(0)` drops the *first* wrapped lines, so an over-length caption keeps its ending and loses its start — with no `…` to signal truncation. This is backwards from the usual convention and confusing on a published video (a caption that appears to start mid-sentence). Fix: pop from the end instead, and/or constrain caption length upstream in the LLM prompt so this path is rarely hit.

- [x] **R1-W9 — Medium: `replay-import` silently destroys previously-learned selectors.**
  `automato/tools/replay_import.py`: `import_replay(..., provider=X)` with no explicit `--out` writes straight to `profiles/<X>/learned.json` via `write_text`, a full overwrite. If the recovery agent had already learned real, production-discovered selectors for that provider, they're gone with no warning and no merge — despite the module's own docstring framing this as a way to "seed" locators, which implies additive, not destructive. Fix: load-merge into any existing file, and/or refuse to overwrite a non-empty target without an explicit `--force`, matching the convention `restore` already uses.

- [x] **R1-W10 — Low-Medium: dead code and broken internal contracts.**
  `automato/adapters/base.py` defines `BaseAdapter` and `AdapterResult`; neither is used anywhere — every real adapter is a bare module-level function, which is also the (correct) pattern `GUIDE_CUSTOMIZATION.md` actually documents. `automato/orchestrator.py`'s `run_workflow(..., only_from_scratch=None)` parameter is accepted and never read. `automato/adapters/publish/youtube_studio.py` computes `vis_selector` from the templated locator and never uses it — the real visibility click is built from a separate, hand-rolled selector a few lines later. None of these break anything today, but each one misleads the next person (or the next agent session) into building on an abstraction nobody actually uses. Fix: delete the unused class/param/variable, or wire it up if it was meant to be load-bearing.

### Future-proof additions (Round 1 — do these alongside the fixes above, not after)

- [x] **R1-F1 — Add automated tests, linting, and CI.** Nothing in this repo would have caught R1-W1 (`NameError`), R1-W2 (missing deps), or R1-W10 (dead/unused variables) except a basic test-and-lint pass: unit tests that import every module and exercise the pure-logic functions (`_parse_script`, `_rebind`, `manifest._validate_manifest`, `_learn_if_stable` with a mocked `page`/`locs`), plus a `ruff`/`pyflakes` run (which flags unused variables and undefined names automatically), both wired into CI on every push. This is the single highest-leverage addition in this entire plan — it would have caught most of Round 1 by itself.
- [x] **R1-F2 — Pin and complete dependencies; document external-binary prerequisites per option.** Pin versions in `requirements.txt`, add the missing TTS packages (R1-W2), and document that `--browser chromium` needs `playwright install chromium` first — the default `edge` channel doesn't, since it drives the already-installed system browser, but that distinction isn't documented anywhere today.
- [x] **R1-F3 — Add a LICENSE file.** The repo is public with no license, which by default reserves all rights and blocks any future distribution or packaging intent.
- [x] **R1-F4 — Centralize every timing/timeout constant into `config.py`.** `generic_llm.py`'s hardcoded 200s deadline, `perchance_images.py`'s `MAX_PER_IMAGE_SEC`/`POLL_INTERVAL_SEC`, and `youtube_studio.py`'s 120s dialog-wait plus several bare `time.sleep(N)` calls are all magic numbers living outside `config.py`, so changing a timing budget in the one documented place doesn't actually change behavior everywhere it should. Do this alongside R1-W7 so it's fixed once, correctly, in every file.
- [x] **R1-F5 — Give the CLI real exit-code semantics (pairs with R1-W4).** Distinct codes for success, an expected/handled failure (e.g. `AuthRequiredError`), and an unexpected crash, plus a one-line "see the log at …" pointer instead of a bare traceback — this is what lets a scheduler or wrapper script actually react to failures instead of just seeing "something exited non-zero."

## Round 2 — Now that Round 1 holds, what does running this for real expose?

*(These either matter only once Round 1's fixes are in place, or become the next bottleneck the moment the pipeline stops crashing on the bugs above.)*

### Weaknesses (ordered by impact)

- [x] **R2-W1 — High: the project is Windows-only by scattered hardcoding, which blocks the CI you just added in R1-F1.** `config.py`'s `BROWSER_EXECUTABLE["brave"]` is a literal `C:\Program Files\...` path; `ffmpeg.py`'s `FONT_CANDIDATES` are four `C:/Windows/Fonts/...` paths with a silent, unlogged fallback to PIL's low-quality bitmap font if none exist; every README/ARCHITECTURE.md example is PowerShell-only. Standard CI runners (including GitHub Actions' default) are Linux, so the new CI from R1-F1 can't actually exercise the local, browser-free `ffmpeg` stage — the one stage the README itself says is fully testable without any account — until this is fixed. Fix: bundle one open-license `.ttf` in the repo as a universal fallback font (and log clearly on fallback), make the Brave path discovered/configurable instead of hardcoded, and add bash equivalents alongside the PowerShell examples.
- [x] **R2-W2 — Medium-High: global mutable config-as-module fights the test suite you just built.** `automato/config.py` is imported and mutated in place at runtime (e.g. `config.DEFAULT_VISIBILITY = args.visibility` in `__main__.py`). This makes tests order-dependent (one test's mutation leaks into the next), blocks safely testing two configurations in one process, and means a typo'd value like `TTS_PROVIDER` isn't caught until it fails deep inside an adapter instead of at startup. Fix: move to a typed, validated settings object (a dataclass with `Literal` fields, or pydantic) built once per run from defaults + env vars + CLI flags, and thread it explicitly through `AdapterContext` instead of relying on a shared global.
- [x] **R2-W3 — Medium-High: no real guard against overlapping scheduled runs.** `automato/browser/session.py`'s per-provider `session.lock` is explicitly advisory — it warns, never blocks (deliberately, so a stale lock after a crash never wedges the engine). But the README documents `--headless` specifically for "unattended scheduled runs," and nothing stops a scheduler from starting a second run while the first is still using the same Chromium profile, risking profile corruption or a hang on Chromium's own internal instance lock. Fix: add a real, staleness-aware process guard for a *full run* (distinct from the existing per-provider advisory lock), and document a minimum scheduling interval.
- [x] **R2-W4 — Medium: no quality gate between "the stage returned a file" and "this is good enough to publish."** A truncated LLM script (still non-empty) is accepted with no minimum-length/sentence-completion check; `perchance_images.py` only guarantees "at least one" of the requested images was captured, not "all requested," and degrades silently with just a log line; the final video's only check is `final.exists()` — no duration/resolution/audio-track/non-silence sanity check. The project already defaults `DEFAULT_VISIBILITY` to `unlisted`, which is a good existing safeguard — but on a run that explicitly opts into `--visibility public` (or a future scheduled-public setup), a quietly degraded run can still go fully live unreviewed. Fix: add explicit thresholds (narration ≥ N words and ends in terminal punctuation; images ≥ 80% of requested or hard-fail; ffprobe-verify the final video has both a video and a non-silent audio stream of roughly the expected duration), and let any soft-fail force a downgrade to `unlisted` even overriding an explicit `public` request, as a last safety net.
- [x] **R2-W5 — Medium: image/prompt correlation in `perchance_images.py` is purely incidental.** It diffs content-hashes of *every* image in *every* frame on the page between polls and takes an arbitrary member of the "new" set — there's no correlation back to which prompt was actually just submitted. Fine today, but fragile against any UI change that shows more than one new image per poll window (e.g. a multi-variant grid). Fix: correlate via the specific generation's DOM container rather than a page-wide diff, where the site's markup allows it.
- [x] **R2-W6 — Medium: three different, subtly inconsistent heuristics for "has the LLM finished streaming."** `generic_llm.py`'s AI Studio loop ends as soon as the substring `"END"` appears *anywhere* (case-insensitively) in the accumulated text — a narration like "...this trend will end soon" would end it early — which is stricter (line-exact) everywhere else in the very same file's `_parse_script`. `llm/chat.py`'s duck.ai loop instead waits for the *entire page's* text to stop changing across polls, which any unrelated dynamic element on the page can reset. `recovery.py` inherits whichever behavior `chat.py` has, since it reuses the same `ask()`. Fix: pick one robust, shared completion signal (e.g. a "stop generating" control's disabled/absent state) and use it everywhere `ask()` is called.
- [x] **R2-W7 — Medium: backup archives are unencrypted despite carrying live sessions.** `automato/backup.py`'s own docstring and the CLI's printed warnings say backups "contain live signed-in sessions" and should be "treated as a secret," and `GUIDE_CUSTOMIZATION.md` explicitly documents shipping these zips between machines — but the tool provides zero technical protection beyond the printed reminder. Fix: add an optional passphrase-encrypted archive mode (e.g. AES via `pyzipper`) and make it the default, with an explicit `--no-encrypt` opt-out rather than the reverse.
- [x] **R2-W8 — Low-Medium: docs describe features and context that don't exist in the repo.** `ARCHITECTURE.md` describes `publish/tiktok.py`, `publish/instagram.py`, and `scripts/login_providers.py`, none of which exist. Multiple `.py` files reference an `AGENTS.md` "contract" and numbered issues (`#7`–`#13`) that also aren't in the repository. Fix: either build the promised adapters/scripts or trim the docs to match reality, and either commit the referenced `AGENTS.md` (folding its contract into `base.py`'s own docstring is enough) or remove the dangling references so nobody — human or agent — goes looking for context that isn't there.

### Future-proof additions (Round 2)

- [x] **R2-F1 — Cross-platform support as a first-class target**, not a side effect of Windows paths happening to exist. Bundle a font, add a Linux CI job (at minimum for the local ffmpeg stage and all pure-logic unit tests; browser-driven stages can stay "manual/live only").
- [x] **R2-F2 — Typed, validated, per-run settings object** replacing the mutable global config module (pairs with R2-W2), with environment-variable overrides for anything that plausibly varies per deployment (visibility default, TTS provider, browser choice).
- [x] **R2-F3 — A real single-run process guard for scheduled/unattended use**, plus a short "how to schedule this safely" doc section with a minimum-interval guard.
- [x] **R2-F4 — Output quality gates + an explicit "review required" downgrade path** (pairs with R2-W4), so publish quality has a floor even when nobody's watching a given run.
- [x] **R2-F5 — A documented content-safety/compliance stance.** Extend the README's existing "Notes & limitations" section with the realistic platform-policy risk of an unattended, generic-description, repeatable-looking upload pipeline — YouTube's monetization policy on repetitive/reused/mass-produced content is the one worth naming explicitly for anyone who opts into `--visibility public` or a real publishing schedule. This is a documentation/mitigation addition, not a code defect: the project's existing `unlisted` default and its deliberate refusal to auto-solve CAPTCHAs (`challenge.py`) already show the right instinct here — make it explicit rather than implicit.
- [x] **R2-F6 — Reconcile documentation with implementation** (finishes R2-W8): one dedicated pass checking that every doc claim has a matching file/behavior and vice versa, before adding anything new on top.

## Round 3 — Steady-state: this project can never reach a literal zero, so make "no weaknesses" a maintained state

*(The pipeline's core dependency is five third-party UIs this project doesn't control, which can change at any time. Round 3 is what's left once Rounds 1–2 land: it turns the remaining, lower-severity items into either fixes or explicitly monitored, accepted trade-offs — the realistic version of "no weaknesses remain" for a browser-automation project.)*

### Weaknesses (ordered by impact)

- [x] **R3-W1 — Medium: selector/UI drift is invisible until a run fails outright.** Even with the LLM-recovery + learned-overlay system (once R1-W1 is fixed), there's no aggregate signal for "recovery is firing much more often this week" — exactly the early-warning sign that a target site changed and the static locators need a real update, not just a per-run patch. Fix: log/count recovery invocations per provider and surface a simple trend; even a local counter file is enough to start.
- [x] **R3-W2 — Medium: the learned-selector overlay never expires or re-validates.** `profiles/<provider>/learned.json` entries are tried *before* the maintained static list, forever, with no timestamp and no re-verification — if a later site redesign leaves a learned selector matching the wrong (but still technically present) element, nothing catches it. Fix: stamp each learned entry with when/why it was learned, and periodically re-validate or expire old ones.
- [x] **R3-W3 — Low-Medium: `ProviderLocations.resolve()` abandons a good candidate on any transient exception.** It moves to the *next* selector in the list rather than retrying the same (likely correct) one first, so a transient timeout on the right element can cause a fallback match against the wrong one. Fix: retry the current candidate once or twice before moving on.
- [x] **R3-W4 — Low-Medium: the global modal-dismiss list can misfire.** `ModalDismisser` clicks the first match from a hardcoded ~16-selector list (`"Skip"`, `"Not now"`, `"Close"`, etc.) before *every* action, on *every* provider, with no per-provider scoping or opt-out — a legitimate, similarly-labeled control in an unexpected flow could get clicked unintentionally, and the logs don't distinguish a correct dismissal from an accidental one. Fix: scope the list per provider where possible, and log what was near the dismissed element for post-hoc auditing.
- [x] **R3-W5 — Low: unbounded dynamic adapter import from workflow JSON.** `manifest.py`'s `_import_adapter` will `importlib.import_module` + `getattr` *any* dotted path found in a workflow file, including a fully-qualified path outside `automato.adapters`. Low risk today since nothing fetches workflows remotely, but `GUIDE_CUSTOMIZATION.md` already encourages shipping workflow+config bundles between machines, and this is a trust boundary that's cheap to close now and expensive to retrofit later. Fix: restrict resolution to an explicit adapter registry/allowlist by default.
- [x] **R3-W6 — Low: assorted small inconsistencies worth batching into one cleanup pass.** `login`'s provider choices include `tts`, even though the README says TTS needs no login; `README.md` states "Python 3.10+" while `ARCHITECTURE.md` states "Python 3.14" verified — pick one supported-versions statement and put it in one place; `state.py`'s `RunState.load()` builds a glob pattern directly from the user-supplied `--resume` id with no escaping (low real-world impact for a local single-user CLI, but a cheap fix).

### Future-proof additions (Round 3)

- [x] **R3-F1 — A scheduled "selector health check."** A manual/monthly CLI subcommand that headedly re-validates each provider's static locators against the live site, independent of a real content run, so drift is caught on a schedule instead of by surprise mid-pipeline.
- [x] **R3-F2 — Staleness policy for learned selectors** (pairs with R3-W2): timestamp on write, automatic expiry or re-verification after N days or M consecutive successful static-selector runs.
- [x] **R3-F3 — Defense-in-depth on adapter resolution** (closes R3-W5): explicit allowlist by default, with a clearly-named opt-in for anyone who deliberately wants to point a workflow at an external module.
- [x] **R3-F4 — A short, honest "accepted trade-offs" section in the README.** Once Rounds 1–2 land, whatever's left — third-party UIs can change without notice; automating a platform's own web UI carries inherent ToS/account risk that an official API would avoid, which this project deliberately trades away to stay API-free and token-free — should be written down as a conscious, monitored choice rather than left as a silent gap. That is the practical, honest meaning of "no weaknesses remain" for a tool whose core dependency is outside its own control.

---

## Closing note

After Round 3, every weakness found in this review is either fixed, mitigated, or turned into an explicit, monitored, accepted trade-off — as close to "no weaknesses remain" as a tool built on automating five third-party UIs can honestly get. Re-running this same review after Round 3 should turn up a *short* Round 4 driven by whatever those third-party sites changed in the meantime, not a rediscovery of anything on this list.
